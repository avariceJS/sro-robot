## Browser session boundary

The signed session cookie uses an explicit 14-day maximum age, `SameSite=Lax` and `HttpOnly`; `Secure` is enabled when `APP_DEBUG=0` and disabled only for local HTTP development. The session secret is required to be at least 32 characters in non-debug mode, and rotating it invalidates cookies signed by the previous value. Each authenticated request reloads the user and rejects a deleted or deactivated account; login clears pre-authentication session data and logout clears the cookie. `revoke-sessions --confirm` provides an explicit global server-side session revocation primitive for controlled key changes; its effects are covered by disposable PostgreSQL tests, not a production identity or secret-management service.

The OCR worker treats claim/setup, local parsing and result persistence as separate failure stages. A parser exception may terminally fail the task through the active lease fence. If persistence of that known parser failure rolls back, the lease stays recoverable after expiry; if its commit acknowledgement is lost, the saved failure remains terminal and is not overwritten. A database/result-persistence exception after a successful parse does not call the terminal failure path: a rolled-back lease-aware result remains recoverable only after lease expiry, while an unleased legacy task remains an unknown `recognizing` item for read-only reconciliation. A lost commit acknowledgement may mean the result already committed, so the worker never overwrites that state with a failure. Claim/setup commit ambiguity also leaves committed work alone; if the claim did not commit, a still-`new` task remains eligible for reconciliation. These paths were exercised with synthetic disposable PostgreSQL fault injection, including rollback, post-commit acknowledgement loss, expiry/reclaim and the lease-disabled legacy path. The SQLAlchemy process-local pool is configurable with `DB_POOL_SIZE` (default `5`), `DB_MAX_OVERFLOW` (default `10`) and `DB_POOL_TIMEOUT_SECONDS` (default `5`). Pool size and timeout must be positive integers; overflow must be non-negative, so SQLAlchemy's unbounded `-1` overflow mode is rejected. Per process, the configured maximum is `DB_POOL_SIZE + DB_MAX_OVERFLOW`; sum this across every web, worker and maintenance process and reserve capacity for migrations/administration before setting values against a PostgreSQL connection budget. A 64-thread synthetic claim probe previously saturated the default pool (49 of 5,000 claims timed out); these knobs enable controlled tuning but do not establish an approved capacity profile. Do not raise defaults without an owner-approved connection budget and representative load/recovery measurements.

On POSIX, startup opens the configured document directory without following a final symlink, checks the opened directory descriptor's owner/type, and applies mode `0700` with `fchmod`; every stored document is written with mode `0600`. A foreign-owned directory or final symlink fails startup before target permissions are changed. This protects against other local OS accounts when the service owns the directory. It is not encryption at rest, backup protection, malware scanning, or a substitute for validating permissions/ACLs on external mounted storage. Existing document files should be checked during deployment; startup currently tightens the directory but does not walk and chmod all historical files. `load_env` opens the secret file without following a final symlink and checks the opened regular file's owner and mode before reading; FIFOs are rejected without blocking. Parent-directory trust and isolation between processes running under the same UID remain deployment responsibilities.

Cookie-authenticated browser mutations require a same-host `Origin` header, or a same-host `Referer` when `Origin` is absent. Requests with neither are rejected. A reverse proxy must preserve the public `Host` header; the check intentionally does not consume request bodies, including multipart uploads. Successful login clears any pre-authentication session data before storing the authenticated user ID. This is a browser CSRF/fixation control, not an authorization or task-ownership policy.

Each authenticated request reloads the user from PostgreSQL. A deleted or inactive account is rejected and its signed-cookie session is cleared on that request; active browser sessions therefore observe account deactivation on the next request. Passwords are verified with Argon2, and a successful login upgrades an older hash to the current configured hasher parameters. This supports gradual parameter changes but is not a password rotation, reset or account recovery process. The accepted policy grants all active employees shared access to all cases and ordinary functions, so individual ownership filters and ordinary-user roles are intentionally absent; technical-administrator separation is not modeled.

`APP_SECRET_KEY` is the single signing key for Starlette's client-side session cookie. There is no overlapping-key verification window. A subtle rollback case matters: changing the key makes old cookies fail signature verification, but restoring the old key can make those cookies valid again while their server-side session rows remain active. For a controlled rotation, first stop and drain every web process so no old-key request can create or finish an authenticated session, then run `.venv/bin/python -m app.cli revoke-sessions --confirm` against the intended database. The command revokes all currently unexpired, unrevoked browser-session rows in one transaction and prints only the aggregate count; without `--confirm` it does not open a database session. Change the managed secret, start all web processes with the same new value, and verify readiness and a synthetic login. If a rollback is needed, the old signing key may be restored only after the global revocation has committed; pre-rotation cookies remain rejected by PostgreSQL. Do not place key material in logs or command-line arguments. This procedure is locally tested guidance, not a managed secret-rotation service or a production deployment exercise; operator identity, access review, audit retention, and web-process draining remain deployment responsibilities.

The global revocation transaction is covered by PostgreSQL regression `test_global_login_session_revocation_prevents_old_key_cookie_reactivation`: it revokes one live session while leaving expired/already-revoked rows unchanged, and repeated execution is a no-op. CLI tests prove missing `--confirm` refuses before database access and successful output contains only an aggregate count. ## Incident checks

1. Check service health, database/Redis availability and worker process/heartbeat.
2. Inspect queue counts and task/event state before retrying.
3. For OCR/acquisition failures, preserve original input and error classification; retry only if operation is idempotent and failure is known pre-side-effect.
4. For any SRO task that may have reached final Save, reconcile read-only before any retry. Unknown means unknown.
5. Record exact evidence and preserve logs; do not restart services or retry jobs blindly.

### Safe response by failure class

- **Process responds but readiness fails:** `/healthz` proves only that the web process answers. Read-only `schema-check`, `ops-status`, and `python scripts/dev/check_compose_runtime_bindings.py` separate schema, queue/worker and local-container findings. A nonzero `ops-status` can mean backlog or a reconciliation condition; it has not changed task or queue state. Do not use `init-db`, Alembic stamp/downgrade, or container recreation as a diagnostic.
- **Schema or database connectivity:** `schema-check` reports the Alembic revision and catalog differences without writing. If the database is unversioned, differs from the expected head, or cannot be reached, stop database-changing commands. Shared adoption requires an independently verified backup, exact schema comparison, DBA review and a maintenance window; source-level verifier success does not authorize any of these.
- **Redis outage, pending outbox, or queue backlog:** run `ops-status` and `outbox-dispatch` without `--apply` first. The former reads aggregates/registries without cleanup; the latter reports durable internal intents. Only use `outbox-dispatch --apply` or `--watch` against a fresh isolated database or a queue whose jobs and outcomes have been reconciled. Never flush/delete Redis data to clear backlog. Redis acceptance may precede a lost client acknowledgement, so treat delivery as at-least-once.
- **Local OCR is queued or recognizing:** `ocr-reconcile` without `--apply` is the read-only candidate count. Apply is available only with `OCR_TASK_LEASES_ENABLED=1` after the lease migration and a single lease-aware worker version is active. Lease-less legacy `recognizing` rows are excluded; expired leased OCR may be reclaimed only through the database fence and bounded attempt policy. Do not start a worker merely because `ops-status` reports one is missing.
- **KAD helper or SRO work is uncertain:** do not repeat a source acquisition after an unknown external result, and do not infer a source result from case number, recency or an empty page. A failed or missing SRO job is never proof that Save did not occur. Keep an unknown outcome unresolved until read-only registry evidence and semantic read-back establish what happened; never automatically retry or mark success from a queue state alone.
- **Document storage or upload failure:** `storage-check` reports permissions without reading document contents; `storage-check --database` also reports aggregate missing/unreferenced/path-reference counts. Preserve the original file and task/audit state; do not repair, overwrite or delete a possibly referenced file by hand. Exercise restore or corruption controls only through the disposable verifier and synthetic files.
- **Credential/configuration change or worker shutdown:** changing `.env.example`, Compose, or source does not change already-running processes or containers. Do not rotate a live DB role, restart a worker, recreate a stateful container, or change Redis authentication until backup integrity, queue contents, application compatibility and a maintenance plan have been reviewed. The current development runtime is not suitable for sensitive documents.

Capture the server-generated request ID, UTC observation time, command exit code and safe aggregate output. Keep user names, case numbers, filenames, document/OCR text, credentials, raw RQ payloads and exception messages out of shared logs. If the available read-only evidence cannot establish whether an operation began or completed, stop at the unknown state and escalate to the system owner/DBA; no production RPO/RTO or on-call response target has been approved.

This decision guide is a repository procedure, not an exercised on-call runbook. Production identity, deployment, escalation contacts, recovery objectives and service-manager actions remain undefined; validate those with the owner and deployment operator before production use.
