Before starting any RQ worker against an existing database or queue, run the read-only `ops-status`. If work is queued or stuck in a processing state, do not start workers until every affected item is identified and its outcome is known. `ops-status` deliberately reports aggregates only, so a positive queue count does not establish that replay is safe. The documented worker command is for a fresh isolated development database or a reconciled queue; the current shared runtime has unresolved queued work and no safe worker restart window.

`ops-status` reports the aggregate timestamp of the oldest task in `new` alongside the oldest `recognizing` update time. The `new` timestamp describes task age, not confirmed Redis enqueue time or a latency/SLA verdict; no task ID, document value or source filename is exposed.

Run server and worker in separate terminals. `create-user` prompts for a local application password and rejects `--password` argv forms without echoing the supplied value. `db-role-check` reports aggregate current-role capabilities plus per-table CRUD, per-sequence privileges and RLS-enabled/forced counts, without role, database or object names; it is a read-only inventory, not a least-privilege policy verdict. Its per-object counts describe PostgreSQL privileges/configuration and do not model row-policy predicates or establish an approved policy. On 2026-10-10 the local development connection reported superuser, CREATEROLE, CREATEDB, replication and BYPASSRLS enabled, as well as database/public-schema CREATE. Do not treat this development role as a production profile. With debug enabled, `MIGRATION_DATABASE_URL` defaults to `DATABASE_URL`; in production, settings require both URLs, distinct explicit PostgreSQL role names, and matching PostgreSQL host/port/database targets. Web/worker services, `schema-check`, and `create-user` use the runtime `DATABASE_URL`; `init-db` preflights through the migration URL and Alembic runs with that same migration credential. The disposable role drill verifies this split: a non-superuser schema owner applies current migrations, while the runtime role receives table/sequence DML privileges and is denied schema DDL and writes to `alembic_version`; both roles pass `schema-check`, future-object default grants are exercised, and the aggregate confirms runtime CRUD across application tables except migration revision writes plus sequence usage. A baseline-versus-patch runtime validation reproduces migration failure under runtime DDL denial, verifies separate-role migration and runtime behavior, and confirms a wrong-database target is refused before changes on the patched side; see [`MIGRATION-ROLE-SPLIT-001`](../post-patch-validation/MIGRATION-ROLE-SPLIT-001_2026-10-11/results-final/report.md). This is a tested configuration boundary, not a production deployment or approved ACL policy. `schema-check` compares the live schema with ORM metadata, native PostgreSQL enum labels/order, public serial sequences, unmodeled views/materialized views/foreign tables/user triggers, RLS enable/force flags and policies, public extensions and routines, index uniqueness, then reports the Alembic revision without changing the database; exit code 1 means schema differences, and 2 means the check could not complete. It does not audit non-public extensions/routines, ACLs or arbitrary PostgreSQL catalog objects. `init-db` applies Alembic migrations only after a read-only preflight: an unversioned database must contain no tables. A populated database without a recorded Alembic revision is refused before migrations run. PostgreSQL migrations acquire a nonblocking session advisory lock; if another migration owns it, the command returns a generic failure and can be retried after the active migration exits. The lock serializes Alembic commands; it does not coordinate application deployments. The current shared database is unversioned and the latest read-only `schema-check` reports seven differences from current metadata: the additive `task_lease` table and its expiry index; the missing append-only event trigger function and trigger set; and the document content-hash index's replacement plus unique-flag drift (also reported by an explicit index comparison because Alembic autogenerate does not detect it). Enum labels/order match and no unmodeled audited objects were found. The aggregate duplicate-hash probe found 18 documents, zero duplicate hash groups and zero excess rows; it did not disclose any hashes. Adoption still requires a verified backup and independent review; only then may a DBA stamp baseline `bc518c7514d3` and apply the pending lease, unique-hash and append-only-audit migrations through current head `a41c72d93e10`. Never auto-stamp or use the command against an unverified schema. The legacy `--reset` flag refuses destructive drops. The baseline downgrade is intentionally blocked. The disposable drill also starts from the lease migration with a synthetic active OCR lease, attempts downgrade to the baseline and verifies refusal preserves the lease row, recognizing task and Alembic revision. From current head it attempts downgrade to base and verifies row/sequence signatures and both identity guards remain unchanged. `/healthz` is a process liveness check. `/readyz` performs bounded PostgreSQL and Redis checks and returns 503 if either is unavailable. It also checks that each non-empty OCR or SRO queue has a worker with a fresh heartbeat; an empty queue does not require a worker. Queue age, oldest-job age, worker capacity and service-level objectives are not measured, and this is not worker supervision.

`ops-status` is a read-only operator snapshot: task counts by state, oldest `recognizing.updated_at`, queue depths, aggregate failed-registry entry counts, per-queue registered RQ worker counts, and aggregate oldest heartbeat age/missing-heartbeat counts. Failed registries are counted with `get_job_count(cleanup=False)`; expired entries are not cleaned and job IDs, results and exception payloads are not read or printed. It does not expose worker names/hosts/PIDs, task IDs or document data, alter task/job state, or enqueue work. Heartbeat age is reported without a stale threshold; alerting and SLA policy remain undefined. An old `recognizing` timestamp is a signal for investigation, not permission to retry; check the actual result and use a fenced recovery path before changing or re-enqueueing work.

Unexpected exceptions in the SRO RQ handler are logged with task ID and exception type only, then replaced with a fixed failure message before RQ stores the failure record/traceback in Redis. The task state is left as-is; failed RQ status is not a retry signal and requires read-only reconciliation before any retry. The guarded disposable Redis smoke verifies a synthetic secret/document sentinel is absent from logs and the persisted traceback, with no task-state change or queued retry. This does not implement a durable external-attempt state machine; live SRO writes remain disabled.

OCR task leases are disabled by default. Enable `OCR_TASK_LEASES_ENABLED=1` only after revision `7af0f5c2d441` has been safely applied, all pre-lease OCR workers have been stopped, the new worker version is deployed, and legacy `recognizing` tasks have been reconciled. Do not run pre-lease and lease-aware OCR workers concurrently: the old handler can write results without checking the lease fence. The lease/fencing protocol applies only to local upload/batch OCR; it never claims KAD or SRO work. `ocr-reconcile` verifies that `task_lease` exists before querying candidate rows; on an older schema it refuses with exit code 2 and an explicit diagnostic, without querying tasks or Redis. On a migrated schema, the default command reports only an aggregate count. `--apply` enqueues new tasks and expired eligible leases only when the feature flag is enabled; task IDs and document data are not printed. Concurrent/duplicate RQ deliveries are safe only when every active OCR worker uses the lease-aware handler.

The OCR worker treats claim/setup, local parsing and result persistence as separate failure stages. A parser exception may terminally fail the task through the active lease fence. If persistence of that known parser failure rolls back, the lease stays recoverable after expiry; if its commit acknowledgement is lost, the saved failure remains terminal and is not overwritten. A database/result-persistence exception after a successful parse does not call the terminal failure path: a rolled-back lease-aware result remains recoverable only after lease expiry, while an unleased legacy task remains an unknown `recognizing` item for read-only reconciliation. A lost commit acknowledgement may mean the result already committed, so the worker never overwrites that state with a failure. Claim/setup commit ambiguity also leaves committed work alone; if the claim did not commit, a still-`new` task remains eligible for reconciliation. These paths were exercised with synthetic disposable PostgreSQL fault injection, including rollback, post-commit acknowledgement loss, expiry/reclaim and the lease-disabled legacy path. This does not qualify the shared pre-lease database or authorize worker startup.

Production configuration must set `APP_DEBUG=0` and provide `APP_SECRET_KEY` with at least 32 characters, plus explicit `DATABASE_URL`, `MIGRATION_DATABASE_URL`, and `REDIS_URL`. Runtime and migration URLs must name distinct explicit database roles. Startup rejects missing values or a shared role rather than falling back to the local development endpoints. Keep secrets in `.env` or the deployment secret store; do not pass them as command-line arguments or include them in logs. The development fallbacks are accepted only while debug mode is enabled. Explicit URLs are not proof that endpoint TLS, authentication or network access is appropriately configured.

The SQLAlchemy process-local pool is configurable with `DB_POOL_SIZE` (default `5`), `DB_MAX_OVERFLOW` (default `10`) and `DB_POOL_TIMEOUT_SECONDS` (default `5`). Pool size and timeout must be positive integers; overflow must be non-negative, so SQLAlchemy's unbounded `-1` overflow mode is rejected. Per process, the configured maximum is `DB_POOL_SIZE + DB_MAX_OVERFLOW`; sum this across every web, worker and maintenance process and reserve capacity for migrations/administration before setting values against a PostgreSQL connection budget. A 64-thread synthetic claim probe previously saturated the default pool (49 of 5,000 claims timed out); these knobs enable controlled tuning but do not establish an approved capacity profile. Do not raise defaults without an owner-approved connection budget and representative load/recovery measurements.

On POSIX, startup opens the configured document directory without following a final symlink, checks the opened directory descriptor's owner/type, and applies mode `0700` with `fchmod`; every stored document is written with mode `0600`. A foreign-owned directory or final symlink fails startup before target permissions are changed. This protects against other local OS accounts when the service owns the directory. It is not encryption at rest, backup protection, malware scanning, or a substitute for validating permissions/ACLs on external mounted storage. Existing document files should be checked during deployment; startup currently tightens the directory but does not walk and chmod all historical files. `load_env` opens the secret file without following a final symlink and checks the opened regular file's owner and mode before reading; FIFOs are rejected without blocking. Keep `.env` mode `0600`; `profile` and `out` directories are restricted to `0700` and must be owned by the service user because browser state/screenshots may contain sensitive data. Parent-directory trust and isolation between processes running under the same UID remain deployment responsibilities.

The authenticated task screenshot route reads only regular `.png` files that are direct children of the configured repository `out` directory. It opens the final path component with `O_NOFOLLOW`; unsupported platforms fail closed. Missing, non-PNG, outside-directory, symlink and non-regular paths return the same not-found response. The response is emitted from the checked file descriptor as `image/png` with `nosniff`, rather than reopening a database-supplied path. This limits filesystem disclosure through a corrupted screenshot-path value; it does not implement employee/task ownership, which remains unresolved.

Treat supplied document samples as confidential local data even when they are untracked and excluded from tests. Restrict sample directories/files at the filesystem level; Git does not preserve private modes for untracked files or directory trees.

Run `.venv/bin/python -m app.cli storage-check` to audit the local document directory without opening file contents. It reports only aggregate counts and fails if the root is not a real directory owned by the service user with mode `0700`, if regular files have another owner or grant group/other access, or if symlinks/unexpected entry types are present. This does not inspect filesystem ACLs, encryption or nested directories.

`Settings.__repr__` excludes the database URL, Redis URL and session-signing key so generic object logging does not expose connection credentials. This is defense in depth; never log the raw environment or settings object.

PostgreSQL new-connection and pool-acquisition waits are capped at five seconds. Redis queue clients use one-second connection and five-second socket timeouts so enqueue/dequeue-related calls do not wait indefinitely during an outage. These are failure bounds, not capacity targets; no 20-user pool sizing or production latency measurement exists.

Cookie-authenticated browser mutations require a same-host `Origin` header, or a same-host `Referer` when `Origin` is absent. Requests with neither are rejected. A reverse proxy must preserve the public `Host` header; the check intentionally does not consume request bodies, including multipart uploads. Successful login clears any pre-authentication session data before storing the authenticated user ID. This is a browser CSRF/fixation control, not an authorization or task-ownership policy.

Each authenticated request reloads the user from PostgreSQL. A deleted or inactive account is rejected and its signed-cookie session is cleared on that request; active browser sessions therefore observe account deactivation on the next request. Passwords are verified with Argon2, and a successful login upgrades an older hash to the current configured hasher parameters. This supports gradual parameter changes but is not a password rotation, reset or account recovery process. This does not yet provide roles or restrict access to tasks owned by another active employee.

`APP_SECRET_KEY` is the single signing key for Starlette's client-side session cookie. There is no overlapping-key verification window: changing the key invalidates existing cookies and requires staff to sign in again. Plan a key change as a coordinated global session revocation; set the replacement through the managed secret source, restart all web processes consistently, and verify login/readiness. Do not place the key in logs or command-line arguments. This is not a managed secret-rotation service or a tested production deployment procedure.

`ops-status` is read-only and reports aggregate task states, the oldest `recognizing` update, queue depth, failed RQ registry counts, worker registrations and heartbeat age without worker identity. If `task_lease` exists, it also counts local upload/batch OCR tasks in `recognizing` with no lease; these legacy tasks require explicit read-only reconciliation and cause exit 1. KAD acquisition is excluded because it has a separate ownership path. If the table is absent, OCR lease classification is reported as unavailable rather than querying a missing relation. The command never starts workers, identifies individual jobs, re-enqueues work or resolves unknown outcomes. Do not start workers against an existing queue based only on aggregate output.

CLI commands are `extract`, `inspect`, and `run`. In the current build, `run` performs local validation and `--live` fails closed. The SRO client also blocks Add, Save and Close by default. Do not enable registry mutations or use a real registry for tests.

The PostgreSQL restore drill starts a disposable PostgreSQL 16 container bound to loopback, applies the application baseline, inserts a synthetic canary plus 20 staff, 10,000 tasks and 10,000 linked events by default, creates a custom-format `pg_dump`, restores into a second database, and checks counts, task/event linkage, expected staff assignment and event actor. It also streams SHA-256 signatures of every application row and PostgreSQL sequence state from both databases, requiring an exact match; a synthetic clone-only update proves the signature check detects changed row data and then restores the clone before continuing. Set `SRO_DRILL_TASKS` from 1 to 100,000 to vary the synthetic task/event volume. It then removes the revision marker and additive lease table only from that restored copy, proves `init-db` refuses the populated unversioned schema, runs the read-only schema comparison, and rehearses an explicit baseline stamp and upgrade on the disposable copy while checking that all canary/workload rows remain. At the end it attempts a head-to-base downgrade in the clone and verifies refusal preserves every application-row/sequence signature, the Alembic head and unique identity guards. The container and temporary upload directory are removed on exit. Never point this script at a shared or production database; the schema is generated from current ORM metadata and the data is synthetic, so this is a migration-path rehearsal, not proof of compatibility with every historical database or owner-approved production volume/RPO/RTO evidence.

Document storage hashes the uploaded bytes with SHA-256 and takes a PostgreSQL transaction advisory lock derived from that hash before checking for an existing `Document`. Concurrent current-version web processes therefore serialize same-content inserts; the transaction releases the lock on commit or rollback. If a rollback/process failure leaves the content-addressed file but no row, a retry reuses that file only after no-follow regular-file/inode checks, service-user ownership, exact POSIX mode `0600`, streamed SHA-256 verification and file/directory re-sync. Partial, mismatched, non-private, symlink and non-regular paths fail closed; they are not deleted automatically. A disposable PostgreSQL test rolled back after file creation, then confirmed same-content admission reuses the verified file and creates the row. This is retry recovery, not orphan cleanup or a retention/deletion policy. Migration `d84f3a210c6b` replaces the non-unique content-hash index with a unique index, providing a persistent guard for legacy/bypassing writers too. The migration aborts without dropping data if duplicate hashes exist. A PostgreSQL integration race test uses eight synthetic concurrent uploads and verifies one stored document row; another verifies the migrated database rejects a duplicate insert that bypasses the service lock. This does not make task creation idempotent: distinct uploads can still create separate tasks referencing the same document, and historical duplicate rows/files are not reconciled. The lock currently uses PostgreSQL's normal lock wait behavior; production admission timeout and overload policy remain unqualified.

## Logging and observability

Upload and KAD task-creation audit events do not duplicate source filenames or case numbers; keep those identifiers in task/document records where the workflow needs them. KAD worker-start events use generic message text while retaining task and actor correlation. Synthetic tests check these boundaries. Unhandled request failures log a server-generated request ID, method, path and exception type without exception text or traceback; the response carries the same ID in `X-Request-ID`. Client-supplied request IDs are ignored. The middleware does not read request bodies. Document-recognition failures log task ID and exception type and persist a generic stage/type message. This avoids accidentally retaining parser messages, file paths or upstream response details, at the cost of omitting stack traces. This is not yet a complete observability system: there are no established structured log schema, metrics, tracing, alerting, queue-age dashboards, heartbeat freshness policy, retention policy or production incident runbook. Do not log raw document/OCR text or credentials.

The same-origin mutation guard rejects repeated `Host`, `Origin` and `Referer` headers rather than letting dictionary construction select one value. Focused middleware tests cover duplicate variants. A baseline-versus-patch runtime validation reproduced duplicate-`Origin` acceptance and duplicate-`Host` acceptance on the prior implementation, verified rejection after the patch, and passed the benign same-origin control, Referer fallback behavior, adjacent malformed-host check and security/logging suites. Evidence: [CSRF singleton-header validation](../post-patch-validation/CSRF-SINGLETON-HEADERS-001_2026-10-11/results-env/report.md).
