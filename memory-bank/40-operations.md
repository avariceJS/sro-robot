# Development, verification and incident handling

## Local development setup (observed)

`deploy/docker-compose.dev.yml` starts only PostgreSQL 16 and Redis 7. FastAPI and RQ workers run from the host `.venv` so OCR can call local Tesseract and Poppler. Defaults in `app/settings.py` use database port `55432`, Redis port `56379`, upload directory `storage/documents`, debug enabled and a development-only session key. These defaults are not production configuration.

`requirements.txt` pins the current Python 3.13 environment. The OCR path additionally needs local Tesseract with Russian data, Poppler, and Playwright Chromium. `.env.example` contains blank placeholders; never print `.env`.

The Compose port mappings are restricted to `127.0.0.1`. Redis is configured for AOF persistence with `appendfsync everysec` on a named volume in future containers; this still permits about one second of queue-write loss and is not a transactional outbox. Containers created from the previous wildcard mappings keep their existing published bindings until recreated. The currently running Postgres/Redis containers were observed bound to `0.0.0.0` and IPv6 wildcard; Redis has no persistent volume/AOF configuration and currently has one queued OCR job. Do not recreate the stack until the queued job has been reconciled/preserved and a restart window is safe. The checked-in changes do not alter existing containers.

Observed local commands:

```bash
docker compose -f deploy/docker-compose.dev.yml up -d
.venv/bin/python -m app.cli init-db
.venv/bin/python -m app.cli create-user 'Test User'
.venv/bin/python -m app.cli schema-check
.venv/bin/python -m app.cli ops-status
.venv/bin/python -m app.cli ocr-reconcile
.venv/bin/uvicorn app.main:app --reload
.venv/bin/rq worker ocr sro --url redis://localhost:56379/0
```

Run server and worker in separate terminals. `create-user` prompts for a local application password and rejects `--password` argv forms without echoing the supplied value. `schema-check` compares the live schema with ORM metadata, native PostgreSQL enum labels/order, public serial sequences and unmodeled views/materialized views/foreign tables/user triggers, then reports the Alembic revision without changing the database; exit code 1 means schema differences, and 2 means the check could not complete. It does not audit extensions, routines, ACLs, policies or arbitrary PostgreSQL catalog objects. `init-db` applies Alembic migrations only after a read-only preflight: an unversioned database must contain no tables. A populated database without a recorded Alembic revision is refused before migrations run. PostgreSQL migrations acquire a nonblocking session advisory lock; if another migration owns it, the command returns a generic failure and can be retried after the active migration exits. The lock serializes Alembic commands; it does not coordinate application deployments. The current shared database is unversioned and read-only `schema-check` reports exactly two expected differences from current metadata: the additive `task_lease` table and its expiry index; enum labels/order match and no unmodeled audited objects were found. Adoption still requires a verified backup and independent review; only then may a DBA stamp baseline `bc518c7514d3` and apply the additive migration. Never auto-stamp or use the command against an unverified schema. The legacy `--reset` flag refuses destructive drops. The baseline downgrade is intentionally blocked. `/healthz` is a process liveness check. `/readyz` checks PostgreSQL and Redis and returns 503 when either is unavailable; it does not check worker presence or queue age.

`ops-status` is a read-only operator snapshot: task counts by state, oldest `recognizing.updated_at`, queue depths and registered RQ worker count. It does not expose task IDs or document data, alter states, or enqueue work. An old `recognizing` timestamp is a signal for investigation, not permission to retry; check the actual result and use a fenced recovery path before changing or re-enqueueing work.

OCR task leases are disabled by default. Enable `OCR_TASK_LEASES_ENABLED=1` only after revision `7af0f5c2d441` has been safely applied, all pre-lease OCR workers have been stopped, the new worker version is deployed, and legacy `recognizing` tasks have been reconciled. Do not run pre-lease and lease-aware OCR workers concurrently: the old handler can write results without checking the lease fence. The lease/fencing protocol applies only to local upload/batch OCR; it never claims KAD or SRO work. `ocr-reconcile` reports a count by default. `--apply` enqueues new tasks and expired eligible leases only when the feature flag is enabled; task IDs and document data are not printed. Concurrent/duplicate RQ deliveries are safe only when every active OCR worker uses the lease-aware handler.

Production configuration must set `APP_DEBUG=0` and provide `APP_SECRET_KEY` with at least 32 characters. Startup rejects a missing or short key in that mode instead of using the development fallback. Keep the key in `.env` or the deployment secret store; do not pass it as a command-line argument or include it in logs. The development fallback is accepted only while debug mode is enabled.

On POSIX, startup requires the configured document directory to be owned by the service user, then restricts it to mode `0700`; every stored document is written with mode `0600`. A foreign-owned directory fails startup before its permissions are changed. This protects against other local OS accounts when the service owns the directory. It is not encryption at rest, backup protection, malware scanning, or a substitute for validating permissions/ACLs on external mounted storage. Existing document files should be checked during deployment; startup currently tightens the directory but does not walk and chmod all historical files. `load_env` rejects a foreign-owned or group/other-accessible POSIX secret file before reading it. Keep `.env` mode `0600`; `profile` and `out` directories are restricted to `0700` and must be owned by the service user because browser state/screenshots may contain sensitive data.

Treat supplied document samples as confidential local data even when they are untracked and excluded from tests. Restrict sample directories/files at the filesystem level; Git does not preserve private modes for untracked files or directory trees.

Run `.venv/bin/python -m app.cli storage-check` to audit the local document directory without opening file contents. It reports only aggregate counts and fails if the root is not a real directory owned by the service user with mode `0700`, if regular files have another owner or grant group/other access, or if symlinks/unexpected entry types are present. This does not inspect filesystem ACLs, encryption or nested directories.

`Settings.__repr__` excludes the database URL, Redis URL and session-signing key so generic object logging does not expose connection credentials. This is defense in depth; never log the raw environment or settings object.

PostgreSQL new-connection and pool-acquisition waits are capped at five seconds. Redis queue clients use one-second connection and five-second socket timeouts so enqueue/dequeue-related calls do not wait indefinitely during an outage. These are failure bounds, not capacity targets; no 20-user pool sizing or production latency measurement exists.

Cookie-authenticated browser mutations require a same-host `Origin` header, or a same-host `Referer` when `Origin` is absent. Requests with neither are rejected. A reverse proxy must preserve the public `Host` header; the check intentionally does not consume request bodies, including multipart uploads. Successful login clears any pre-authentication session data before storing the authenticated user ID. This is a browser CSRF/fixation control, not an authorization or task-ownership policy.

Each authenticated request reloads the user from PostgreSQL. A deleted or inactive account is rejected and its signed-cookie session is cleared on that request; active browser sessions therefore observe account deactivation on the next request. This does not yet provide roles or restrict access to tasks owned by another active employee.

CLI commands are `extract`, `inspect`, and `run`. In the current build, `run` performs local validation and `--live` fails closed. The SRO client also blocks Add, Save and Close by default. Do not enable registry mutations or use a real registry for tests.

## Test commands

```bash
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m compileall -q app sro_robot tests
git diff --check
bash scripts/dev/postgres-restore-drill.sh
scripts/dev/verify.sh
```

The PostgreSQL restore drill starts a disposable PostgreSQL 16 container bound to loopback, applies the application baseline, inserts a synthetic canary plus 20 staff, 10,000 tasks and 10,000 linked events by default, creates a custom-format `pg_dump`, restores into a second database, and checks counts, task/event linkage, expected staff assignment and event actor. It requires zero synthetic identity-link mismatches. Set `SRO_DRILL_TASKS` from 1 to 100,000 to vary the synthetic task/event volume. It then removes the revision marker and additive lease table only from that restored copy, proves `init-db` refuses the populated unversioned schema, runs the read-only schema comparison, and rehearses an explicit baseline stamp and upgrade on the disposable copy while checking that all canary/workload rows remain. The container and temporary upload directory are removed on exit. Never point this script at a shared or production database; the schema is generated from current ORM metadata and the data is synthetic, so this is a migration-path rehearsal, not proof of compatibility with every historical database or owner-approved production volume/RPO/RTO evidence.

Verified on 2026-10-10 at the upper supported drill size with `SRO_DRILL_TASKS=100000 bash scripts/dev/postgres-restore-drill.sh`: 100,000 task/event pairs and 20 synthetic staff restored with zero checked identity-link mismatches; canary preservation, populated-schema refusal and clone-only baseline/additive migration passed, as did all 8 PostgreSQL lease/concurrency/process-restart tests. The drill also ran the feature-disabled legacy OCR handler against the baseline schema before migration and verified its task state/audit event from a fresh process after migration. This is sequential process-change compatibility for the additive migration, not evidence that old and lease-aware writers may overlap (they must not). Cleanup left no drill container or temporary upload directory. This is a correctness/restore rehearsal at that data volume, not a throughput, queue-latency or soak test and not an owner-approved office workload profile.

On 2026-10-10, a separate one-off rehearsal used a private temporary logical dump of the actual shared development DB and restored it into a disposable PostgreSQL 16 clone. It compared internal row/link signatures and sequence state before and after the clone-only baseline stamp and current additive OCR-lease migration; compared data remained identical. The clone had exactly the expected lease table/index schema differences, with enums and other audited public objects matching. The source DB remained unversioned and was not stamped or migrated. The temporary dump and clone were deleted after verification, so this is not a retained or scheduled backup and establishes no production backup coverage, RPO or RTO. It does not authorize changing the source DB. For any future adoption, first create and retain a separately verified backup under an approved operational process, review the exact source schema/data compatibility, and arrange a controlled outage that stops every legacy OCR writer before lease-mode rollout.

It requires the pinned `.venv` by default and a working Docker daemon; set `SRO_ROBOT_PYTHON` to another compatible interpreter when needed.

No task was retried or inspected. ## Logging and observability

Upload creation audit events do not duplicate the source filename; keep filenames only in the document record, where the workflow needs them. Unhandled request failures log a server-generated request ID, method, path and exception type without exception text or traceback; the response carries the same ID in `X-Request-ID`. Client-supplied request IDs are ignored. The middleware does not read request bodies. Document-recognition failures log task ID and exception type and persist a generic stage/type message. The owner-pending KAD worker changes in the current worktree apply the same redaction but remain uncommitted. This avoids accidentally retaining parser messages, file paths or upstream response details, at the cost of omitting stack traces. This is not yet a complete observability system: there are no established structured log schema, metrics, tracing, alerting, queue-age dashboards, worker heartbeat, retention policy or production incident runbook. Do not log raw document/OCR text or credentials.

Every background job needs a durable task correlation ID, explicit result/state transition and enough diagnostic context to reproduce failure without exposing document contents. Avoid silently swallowing cleanup/close errors.

## Incident checks

1. Check service health, database/Redis availability and worker process/heartbeat.
2. Inspect queue counts and task/event state before retrying.
3. For OCR/acquisition failures, preserve original input and error classification; retry only if operation is idempotent and failure is known pre-side-effect.
4. For any SRO task that may have reached final Save, reconcile read-only before any retry. Unknown means unknown.
5. Record exact evidence and preserve logs; do not restart services or retry jobs blindly.

Last observed runtime (2026-10-10): app health HTTP 200; Postgres/Redis healthy; no RQ workers; one OCR queued, five OCR failed (empty zero-byte uploads), one SRO failed after unexpected worker termination. Do not assume this state remains current.
