# Состояние проекта

Обновлено: 22.09.2026

## Готово и проверено

- OCR фото и PDF, многопрогонное распознавание с голосованием.
- Извлечение 13 полей, контрольные суммы ИНН и СНИЛС, падежи ФИО, пол по отчеству.
- Разбор адреса по полям модалки (индекс, регион, район, город, улица, дом, кв).
- Экран проверки в консоли: точность по каждому полю и предупреждения.
- Робот СРО: вход с сохранением сессии в `profile/`, переход в реестр физлиц,
  поиск дублей сначала по ИНН потом по ФИО, заполнение карточки и адреса,
  скриншоты каждого шага в `out/`.
- Пробный прогон (`run` без `--live`) отработал на всех трёх образцах: форма
  заполняется правильно, черновик закрывается без записи.
- Код разделён на слои `core / platform / scenarios / documents` (22.09.2026),
  у сценариев единый контракт (`scenarios/base.py`), консоль его только вызывает.

Это примерно 30% ручной работы компании.

## Не проверено

**Запись в СРО с `--live` ни разу не запускалась.** Владелец сознательно не
тестирует на вымышленных должниках, чтобы не мусорить в реальном реестре.
Непроверенными остаются: нажатие «Сохранить» на карточке, сохранение модалки
адреса, поведение платформы после записи.

выгоднее собрать ядро на одном готовом сценарии и подключать к нему остальные
фичи, чем натягивать веб на три готовых сценария. Архитектура ядра —
`25-web-platform.md`.

1. ~~**Разделение на слои** `platform / scenarios / documents / core`~~ —
   сделано 22.09.2026. Карточка физлица живёт в `scenarios/person_card.py`,
   контракт описан в `20-architecture.md`. Пробный прогон после разделения
   проверен на локальной копии формы; **живой `run` на платформе владелец ещё
   не перезапускал** — платформа недоступна с машины, где шёл рефакторинг.
2. ~~**Скелет `app/`**~~ — сделано 22.09.2026: вход сотрудника по логину вида
   «Иванова М.И.», боковое меню как в СРО, загрузка, распознавание в фоновом
   воркере, экран проверки по `scenario.fields`, подтверждение оператором,
   остановка робота на заполненной форме со снимками и решением оператора,
   журнал событий. Проверено на образцах 1 и 2 и на локальной копии формы;
   запись в СРО ожидаемо падает на недоступности платформы с машины
   разработки. Миграций пока нет, схема создаётся `app.cli init-db`.
3. **Очередь и пакетная загрузка**: очередь уже работает (RQ), осталось

4. **Сессии СРО на пользователя**: процесс с браузерным контекстом, таймаут
   простоя, первый `--live` из веба под присмотром.
5. **Журнал дел**: номер дела занимается сотрудником, двое не берут одно дело.
6. **Приём с почты и из папки сканера** — адаптеры к тому же конвейеру.
7. **Docker Compose и российский VPS**, с проверкой доступности платформы с его IP.

(`/register/assignment_list.aspx`), профили извлечения под заявления и решения.
Перед каждым — `inspect` соответствующего реестра.

## Открытые вопросы

- Доступна ли платформа с IP российского VPS (адреса дата-центров блокируются
  чаще всего). Проверить почасовым VPS до оплаты.
- Есть ли у вендора `sro-service.ru` API или массовый импорт. Если да — браузерная
  автоматизация заменяется HTTP-запросами. Вопрос вендору пока не задан.
- Сколько памяти потребует пул браузеров на 6–15 сотрудников с личными учётками.
