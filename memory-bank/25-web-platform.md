# Веб-платформа: ядро, куда подключаются фичи

Решение о постройке принято 22.09.2026. Цель — ядро, в которое новая
возможность (карточка организации, назначение, новый тип документа)
добавляется файлом сценария и строкой регистрации, без правки ядра.

## Два репозитория внутри одного проекта

```
sro_robot/     # библиотека: core, platform, scenarios, documents, cli
app/           # веб-приложение поверх библиотеки
```

Зависимость строго в одну сторону: `app` импортирует `sro_robot`, обратно —
никогда. Консольный `cli.py` остаётся рабочим: это самый дешёвый способ
отладить сценарий без веба.

```
app/
  db/         # модели SQLAlchemy, миграции Alembic
  intake/     # приём документов: upload, mailbox, folder — общий интерфейс
  services/   # задания, журнал дел, поиск дублей, аудит
  workers/    # ocr_worker (без состояния), sro_worker (сессия на пользователя)
  api/        # роуты FastAPI
  web/        # шаблоны Jinja + HTMX
deploy/       # Dockerfile, docker-compose, nginx
```

## Главное ограничение: ядро не знает про физлиц

`DebtorCard` описывает физическое лицо и как вход платформы не годится:
у организации ИНН, ОГРН, КПП и наименование, а назначение — вообще не карточка
лица, а связка дела, должника и управляющего.

Поэтому ядро оперирует **заданием**: тип сценария, документ, набор полей
`Field(value, confidence, source, warning)` в JSONB и статус. Что это за поля,
ядро узнаёт у сценария через `scenario.fields` — тот же контракт, что уже
используется консолью. Экран проверки строится по этому объявлению, а не по
жёсткому списку полей физлица.

## Модель данных

| Таблица | Что хранит | Чего не хранит |
| --- | --- | --- |
| `user` | сотрудник: вход в приложение, роль, его логин СРО | **пароль СРО** |
| `document` | файл, хеш, кто и откуда загрузил, страницы | — |
| `task` | задание: сценарий, профиль документа, поля OCR и поля после правок оператора, статус, номер дела, исполнитель, ссылка на запись в СРО | — |
| `case_claim` | журнал дел: номер дела занят сотрудником | — |
| `event` | аудит: кто, что, когда, чем кончилось | сканы и сырой текст |
| `sro_session` | состояние сессии СРО пользователя, путь к профилю браузера | пароль |

Хеш файла нужен, чтобы один и тот же скан, пришедший и почтой, и из папки
сканера, не превращался в два задания.

## Жизненный цикл задания

```
new -> recognizing -> needs_review -> approved -> writing -> done
                           |                        |
                           +-> rejected             +-> failed / duplicate
```

`needs_review` обязателен: человек из процесса не убирается (см. `10-project.md`).
Запись в СРО начинается только после `approved` живым человеком — это веб-аналог
нынешнего вопроса «Данные верны?» в консоли и того же правила, что `--live`
не нажимается сам.

## Три режима приёма — один интерфейс

Адаптер приёма делает одно: кладёт файл и создаёт `document` + `task`. Дальше
конвейер общий, поэтому все три режима стоят почти как один.

| Режим | Адаптер | Когда |
| --- | --- | --- |
| Один документ | `intake/upload.py` | оператор загрузил, ждёт результат |
| Пачка сканов | `intake/upload.py` | загрузил 50 файлов, разбирает очередь по одному |
| Почта и папка сканера | `intake/mailbox.py`, `intake/folder.py` | документы приезжают сами |

## Сессии СРО: воркер на пользователя

Каждый работает под своей учёткой СРО — так в журнале самой СРО видно, кто
завёл карточку (решение от 20.09.2026). Из этого следует устройство воркеров:

- OCR — обычный пул процессов, состояния нет, масштабируется числом воркеров.
- Запись в СРО — **процесс на пользователя**, внутри живой Playwright-контекст
  с его профилем. Задания одного пользователя выполняются строго по одному:
  платформа СРО — WebForms с общим состоянием страницы, параллельные вкладки
  одной сессии ломают постбэки.
- Простой дольше таймаута закрывает браузер. Профиль на диске хранит куки,
  поэтому повторное открытие не требует пароля.
- Пароль СРО принимается один раз при входе в сессию, живёт в памяти процесса
  до создания куки и в базу не пишется.

Сколько памяти займут 6–15 браузеров — открытый вопрос, меряем на первом
нагруженном дне. Отсюда таймаут простоя и очередь, а не браузер на каждого
залогиненного.

## Стек и почему такой

| Решение | Причина |
| --- | --- |
| Python 3.12, FastAPI | ядро робота уже на Python, второй язык в проекте некому поддерживать |
| PostgreSQL + SQLAlchemy 2.0 + Alembic | JSONB для полей задания, честные блокировки для журнала дел, миграции |
| Jinja2 + HTMX, без SPA | внутренний инструмент на 6–15 человек; React означал бы вторую сборку и второй деплой при одном разработчике |
| Redis + RQ | очередь OCR и очереди пользователей, наблюдаемость из коробки |
| Docker Compose на российском VPS | ПД не уезжают к чужому провайдеру, разворачивание одной командой |

«Мощное и поддерживаемое» здесь означает меньше движущихся частей, а не больше
технологий: всё перечисленное — один язык, один процесс сборки, один compose-файл.

## Как запустить локально

```bash
docker compose -f deploy/docker-compose.dev.yml up -d      # Postgres 55432, Redis 56379
.venv/bin/python -m app.cli init-db
.venv/bin/python -m app.cli create-user 'Иванова М.И.'     # пароль спросит скрытым вводом
.venv/bin/uvicorn app.main:app --reload                    # интерфейс на 127.0.0.1:8000
.venv/bin/rq worker ocr sro --url redis://localhost:56379/0  # в отдельном окне
```

Воркер запускается из `.venv`, а не в контейнере: OCR пользуется системными
`tesseract` и `poppler`. Без запущенного воркера задание навсегда останется в
статусе «принят» — это первое, что нужно проверить, если ничего не распознаётся.

## Что уже работает (22.09.2026)

Загрузка одного файла и пачки, распознавание в фоне, экран проверки с полями из
`scenario.fields`, правка и подтверждение оператором, пробный прогон сценария в
отдельном воркере, журнал событий и показ ошибки на странице задания.

Вход по логину как в СРО («Иванова М.И.»), без почты. Боковое меню повторяет
меню платформы: работает только «Физические лица», остальные разделы серые.

## Остановка на заполненной форме

Робот не закрывает черновик сам. Заполнив карточку, он зовёт `ReviewGate`:
`DbReviewGate` кладёт снимки формы в задание, ставит статус `awaiting_preview`
и раз в секунду смотрит в базу, не ответил ли оператор. На странице задания
появляются снимки и две кнопки: «Закрыть без записи» и «Сохранить в СРО…»,
причём вторая ведёт на отдельный экран подтверждения.

Пока оператор смотрит, воркер очереди `sro` занят этим заданием — это осознанно:
браузер с открытой формой нельзя отдать другому заданию. Таймаут ожидания —
10 минут, дальше черновик закрывается. Запас у очереди больше таймаута
(`default_timeout=900`), иначе RQ убьёт задание раньше.

В консоли то же самое делает `--preview`:

```bash
.venv/bin/python -m sro_robot run samples/opredelenie_1.jpg --preview
```

Не сделано: сессии на пользователя (пока общая учётка из `.env`), журнал занятых
дел, приём с почты и из папки, контейнер приложения и VPS.

## Как добавляется новая фича

1. `python -m sro_robot inspect --registry firm` — снять структуру формы.
2. Селекторы в `platform/pages.py` новым словарём.
3. Файл в `scenarios/`, контракт из `scenarios/base.py`, образец — `person_card.py`.
4. Профиль документа в `documents/`, если тип документа новый.
5. Регистрация в `scenarios/__init__.py`.

Веб, база и экран проверки не правятся: они работают через контракт.
